План: память агента

Статус: готов к разработке
Как владелец, я хочу, чтобы Majordomo помнил важное обо мне и о наших прошлых разговорах, чтобы не повторять одно и то же и возвращаться к старым темам.

1Задача

Сейчас Majordomo не помнит ничего между диалогами: после /new он начинает с нуля. В длинном диалоге старые сообщения выпадают из запроса: модель видит только последние 50. План даёт агенту память о владельце и поиск по прошлым разговорам.

Вопросы владельца и где ответ

  1. Где хранится память — раздел 4 (ER-схема) и карта компонентов.
  2. Что попадает в контекст каждой сессии — таблица «Контекст хода».
  3. Кто, когда и как пишет в память — схемы «Запомни» и «Обработка диалога», правила П1, П2, П10, П11.
  4. Как агент получает знания сверх контекста — таблица тулов и схема «Ход».
  5. Кто следит за актуальностью и дублями и что лежит в ядре — схема «Ночная консолидация», правила П3, П7, П12, П17.
  6. «А помнишь, позавчера мы обсуждали…» — сценарий S4 и схема «Поиск по истории».

Пути шаг за шагом

Схема последовательности по UML: участники сверху, время идёт вниз. Сообщение идёт только от вызывающего к вызываемому, ответ возвращается тем же путём. Рамки — фрагменты: в alt выполняется одна ветка, в opt — шаги при условии, в loop — повтор.

Контекст хода

Что модель получает на каждом ходу, в этом порядке.

Блоки 1–2 — системный промпт: транспорт кладёт его в instructions, в начало запроса (факт 11). Блок 3 — первое сообщение role user в рамке <summary>: сводку пишет модель, поэтому прав инструкций у неё нет. Блок 1 собирается из кода, блоки 2–3 — каждый ход обычным SQL, без модели. Блок 2 стоит в рамке <memory>. Записи memory.entries в контекст не попадают: их находит memory_search. Прошлых диалогов в контексте нет: их находит history_search. В веб-чате блоков 3 и 4 нет: историю присылает клиент (факт 5).

Почему ядро собирается каждый ход, а не снимком на диалог: оно меняется редко, поэтому начало запроса почти всегда совпадает с прошлым ходом и кэшируется, а новый факт виден сразу. Блок 1 меняется только с деплоем. Время уходит в хвост: оно меняется каждый ход (факт 11).

Блок 1 по секциям

Секции идут в этом порядке (П19), каждая — в своём теге.

Возможность — { name, rules, tools(turn) } из apps/core/src/lib/capability.ts: имя, строки правил и набор тулов на ход. Правила меняются только с деплоем, набор тулов зависит от канала и id диалога. agent.ts объединяет наборы в параметр tools вызова streamText: описания и схемы тулов провайдер передаёт модели отдельно от промпта. Поэтому правило про одно поле тула пишется в .describe() его схемы, а в rules — только правила, которые связывают несколько тулов.

Почему справочников учёта в промпте нет: категории отдаёт list_categories, неизвестную валюту тул отклоняет с понятной ошибкой (факт 17). Новая категория не меняет начало запроса. Что главнее при конфликте указания владельца и правила возможности — последняя строка <principles>.

        Тулы памяти

        Ожидаемый сбой тул возвращает значением { error: { code, message } }, как тулы учёта (факт 14). В веб-чате есть только memory_search. Набор тулов собирается на каждый ход: с id диалога в Telegram и без него в веб-чате.
