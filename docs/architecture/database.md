# База данных и миграции

Одна база Postgres в Neon. Её используют сервер на Vercel (`apps/core`) и будущие воркеры DBOS. Для локальной разработки есть отдельный Postgres в Docker.

## Одна база, отдельная схема на каждый домен

| Схема Postgres                  | Кто владеет и мигрирует                    | Что внутри                                                          |
| ------------------------------- | ------------------------------------------ | ------------------------------------------------------------------- |
| `auth`                          | `packages/db` (Drizzle)                    | токены внешних сервисов (ChatGPT и будущие интеграции), зашифрованы |
| `chat`                          | `packages/db` (Drizzle)                    | диалоги с владельцем в каналах (Telegram), их история и ходы агента |
| `finance`, `tools`, `memory`, … | `packages/db` (Drizzle), по мере появления | предметные данные                                                   |
| `dbos`                          | DBOS (его собственные миграции)            | состояние workflow, очереди, расписания                             |
| `drizzle`                       | Drizzle                                    | журнал применённых миграций `__drizzle_migrations`                  |
| `public`                        | никто                                      | не используется                                                     |

Почему схемы в одной базе, а не несколько баз:

- Транзакции и внешние ключи работают между доменами. Шаги DBOS (datasource-транзакции) могут писать в предметные таблицы в той же транзакции, что и отметка о выполнении шага.
- Доступ разграничивается по схемам. Например, `finance` позже можно открыть только отдельной роли.
- Одна строка подключения, одна резервная копия, одна ветка Neon на preview.

Новый домен добавляется так:

1. Создать файл `packages/db/src/schema/<домен>.ts` с `pgSchema("<домен>")`.
2. Экспортировать его из `schema/index.ts`.
3. Добавить схему в `schemaFilter` в `drizzle.config.ts`.

Схемы `dbos` и `drizzle` в `schemaFilter` не попадают никогда. Иначе drizzle-kit решит, что это лишние таблицы.

## Где хранится схема

- **Источник правды:** TypeScript-описание в `packages/db/src/schema/`.
- **Миграции:** SQL-файлы в `packages/db/migrations/`, сгенерированные drizzle-kit. Они коммитятся вместе с кодом, который их использует. Это то, что реально выполнится в базе, поэтому SQL читается на ревью.
- Уже применённые миграции не редактируются. Ошибка исправляется новой миграцией.

## Как меняется схема

```sh
# 1. Поменять packages/db/src/schema/*.ts
# 2. Сгенерировать миграцию и прочитать получившийся SQL
pnpm --filter @repo/db db:generate --name add_finance_accounts
# 3. Применить к своей базе (ветке Neon или локальному Postgres)
DATABASE_URL_UNPOOLED=postgres://… pnpm --filter @repo/db migrate
# 4. Закоммитить схему, миграцию и код вместе
```

Правила:

- **Только обратно совместимые изменения (expand/contract).** Миграция применяется до выкладки нового кода. Если сборка после неё упадёт, в production продолжит работать старый код уже на новой схеме. Instant Rollback в Vercel откатывает код, но не схему.
  - Новые колонки должны быть nullable или иметь default.
  - Переименование и удаление делаются в два деплоя: сначала код перестаёт использовать колонку, потом колонку удаляют.
- **Миграцию генерировать на свежем `main`.** Drizzle 0.45 применяет только миграции новее последней применённой. Если ветка с более старой миграцией смёржится после более новой, старая молча не применится. Поэтому перед мёржем, если в `main` появились другие миграции, свою надо перегенерировать.
- **Без `CREATE INDEX CONCURRENTLY` в миграциях Drizzle.** Все миграции выполняются в одной транзакции. Для индексов на больших таблицах нужен отдельный ручной шаг.

## Кто и когда запускает миграции

**Сборка на Vercel** (`apps/core/vercel.json`):

```
pnpm --filter @repo/db migrate && pnpm turbo run build --filter=@repo/core
```

- Миграции идут до `next build`, то есть до того, как новый код начнёт принимать запросы.
- Скрипт запускается вне turbo, потому что turbo в строгом режиме скрывает переменные `VERCEL_ENV` и `DATABASE_URL_UNPOOLED`.
- **Production** мигрирует всегда.
- **Preview** мигрирует только при `MIGRATE_PREVIEW_DATABASES=true`. Эту переменную включают, только когда в интеграции Neon настроены отдельная ветка на каждый preview и опция «Resource must be active before deployment». Без этого preview получил бы адрес production-базы.
- Скрипт использует прямое подключение `DATABASE_URL_UNPOOLED`. Пуловый адрес Neon (`-pooler`) он отклоняет: PgBouncer в режиме транзакций ломает блокировку и многооператорные миграции.
- Скрипт держит advisory lock, поэтому две одновременные сборки мигрируют по очереди.

**Локально** база работает в Docker (`compose.yaml`, Postgres 17): `pnpm db:up`. Миграции запускаются вручную: `pnpm db:migrate`. Адрес берётся из `apps/core/.env.local`. Для локальной базы задаётся свой `SECRETS_ENCRYPTION_KEYS`, ключ production туда не копируется.

**Тесты `@repo/core`** работают с тем же контейнером, но с отдельной базой `majordomo_test`: глобальная настройка Vitest (`apps/core/vitest.global-setup.ts`) поднимает контейнер, пересоздаёт эту базу и применяет к ней миграции тем же `migrate.ts`. Адрес задан в `apps/core/vitest.config.ts`, `.env.local` не читается. **E2e-тесты** (Playwright) так же пересоздают свою базу `majordomo_e2e` (`apps/core/e2e/global-setup.ts`, адрес в `apps/core/e2e/env.ts`), а сервер e2e работает с ней. Обе настройки (`apps/core/test-database.test-utils.ts`) пересоздают только базы с именем `*_test` или `*_e2e` на сервере из `compose.yaml` (`127.0.0.1:5432`), поэтому неверный адрес не заденет ни базу разработки, ни другой сервер.

**Никогда при старте функции.** На Vercel одновременно живёт много экземпляров, и они бы мигрировали наперегонки. То же касается DBOS.

## DBOS

Пока не подключён. Когда появится:

- Хранит состояние в той же базе, в схеме `dbos` (`systemDatabaseSchemaName`).
- Подключается через `DATABASE_URL_UNPOOLED`: DBOS не поддерживает PgBouncer в режиме транзакций. Пул на экземпляр держать маленьким (2–3 соединения), потому что у Neon ограничено число прямых подключений.
- Его системные таблицы мигрирует тот же `packages/db/src/migrate.ts` через `DBOS.migrate(url, { schemaName: "dbos" })`. Сам DBOS запускается с `runMigrations: false`.
- `applicationVersion` задаётся явно. Иначе каждый деплой оставляет незавершённые workflow прошлой версии без исполнителя.

**Ограничения DBOS на Vercel.** Их стоит учесть до того, как строить на нём логику:

- DBOS не советует запускать его внутри процесса Next.js. На Vercel рекомендуемая схема — отдельный route-воркер, который будит cron, а Next.js ставит задачи через `DBOSClient`.
- Очереди, `sleep` и расписания продвигаются, только пока воркер жив. **На Hobby cron срабатывает раз в сутки**, значит и фоновые задачи шли бы раз в сутки. На Pro cron можно запускать раз в минуту.
- Все экземпляры функций для DBOS — один исполнитель `local`. Каждый холодный старт заново подхватывает незавершённые workflow, так что шаги выполняются «хотя бы один раз» и должны быть идемпотентными.
- Альтернатива — отдельный постоянно работающий воркер (Fly.io, Railway, VPS) с той же базой Neon. Тогда Vercel только принимает запросы и ставит задачи.

## Секреты в базе

- Токены шифруются `SecretBox` (AES-256-GCM, `packages/db/src/secret-box.ts`) до записи в базу. Шифротекст привязан к таблице и строке.
- Ключи лежат в `SECRETS_ENCRYPTION_KEYS`. Переменная обязательна во всех окружениях: без неё сервер не собирается и не стартует (`apps/core/src/lib/config.ts`).
- У Production и у Preview **разные ключи**. Ключ production задаётся только для окружения Production, а preview получает свой. Копия базы в preview-ветке Neon или в дампе без ключа production бесполезна: preview не расшифрует токены production, ручки ответят 500.
- Свой ключ не мешает preview **писать** в базу: вход и выход в ChatGPT перезаписывают и удаляют строки с токенами. Поэтому preview-деплои допустимы, только когда у каждого preview своя ветка Neon (см. `MIGRATE_PREVIEW_DATABASES` выше). Иначе preview получит адрес production-базы и сможет испортить сессию production.
- Ротация ключа: новый ключ ставится первым в списке, секреты перезаписываются, затем старый ключ убирается.
- Ключ хранится вне Neon (менеджер паролей). Без него резервная копия базы не восстановит токены, но их можно получить заново входом.

## Переменные окружения сервера

Сервер читает переменные один раз при старте (`apps/core/src/lib/config.ts`, его загружает `src/instrumentation.ts`, а `next build` — вместе с модулями ручек). Если обязательной переменной нет или она задана неверно, сборка и старт падают со списком всех ошибок. После старта код берёт значения из `config` без проверок. Чтобы `next build` видел эти переменные под turbo, они перечислены в `passThroughEnv` задачи `build` в `turbo.json`. `DATABASE_URL_UNPOOLED` и `MIGRATE_PREVIEW_DATABASES` читает только скрипт миграций.

| Переменная                     | Откуда                     | Зачем                                               |
| ------------------------------ | -------------------------- | --------------------------------------------------- |
| `DATABASE_URL`                 | интеграция Neon            | пуловое подключение для запросов                    |
| `DATABASE_URL_UNPOOLED`        | интеграция Neon            | миграции, в будущем DBOS                            |
| `SECRETS_ENCRYPTION_KEYS`      | вручную, своя на окружение | шифрование токенов (`openssl rand -base64 32`)      |
| `MAJORDOMO_API_TOKEN`          | вручную                    | токен владельца для клиентов, не короче 32 символов |
| `CRON_SECRET`                  | вручную                    | авторизация Vercel Cron                             |
| `OPENAI_MODEL`                 | вручную, необязательно     | модель агента                                       |
| `MIGRATE_PREVIEW_DATABASES`    | вручную, необязательно     | миграции на preview-ветках Neon                     |
| `ENABLE_EXPERIMENTAL_COREPACK` | вручную, `1`               | сборка на pnpm 11 из `packageManager`               |

## Первый деплой

1. Vercel → New Project → этот репозиторий, Root Directory `apps/core`. Node.js 24 берётся из `engines`. Опция «Include files outside the Root Directory» должна быть включена: сборке нужны пакеты из `packages/`.
2. Подключить Neon через Vercel Marketplace. Интеграция задаст `DATABASE_URL` и `DATABASE_URL_UNPOOLED`.
3. Задать переменные из таблицы выше. `SECRETS_ENCRYPTION_KEYS` задаётся дважды: ключ production — только для Production (форма Vercel по умолчанию отмечает все окружения, лишние галочки надо снять), отдельный ключ — для Preview и Development.
4. Задать `ENABLE_EXPERIMENTAL_COREPACK=1` для всех окружений. Сам Vercel ставит pnpm не новее 10, а проект использует pnpm 11 (`allowBuilds`, проверка возраста релизов). С Corepack Vercel берёт версию из поля `packageManager` в корневом `package.json`. В логе сборки должно быть видно pnpm 11.
5. Задеплоить. Сборка применит миграции.
6. Отправить с клиента запрос к `/api/agent`. Сервер ответит `409 openai_login_required` со ссылкой и кодом. Открыть ссылку на телефоне, ввести код, опрашивать `GET /api/openai/login`, пока не придёт `complete`.
